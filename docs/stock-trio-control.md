# Stock Trio bolus control

This is a separate opt-in, manually confirmed bolus workflow using unmodified Trio v1.0.2's existing remote-command protocol. The response-history patch is optional and is not a prerequisite. TrioPC does not change your phone app, dosing algorithm or pump driver.

This prototype has not been validated by sending a live bolus. Implementation checks used synthetic fixtures and mocked transports only. It provides no dose calculation or recommendation, no remote bolus cancellation, and no verified completion or partial-delivery status.

## Setup in the Mac app

1. Connect your existing Nightscout server. In the **Bolus** workspace, expand Connection and control settings and select Read Trio profile from Nightscout. The newest profile must contain Trio's bundle identifier, team, device token and APNs environment. These are read from `/api/v1/profile.json?count=1`. If missing or stale, upload the current profile through Trio's existing Nightscout settings. Stock Trio's existing Remote Control setting must be enabled with its shared secret; no rebuild is required for that setting.
2. Verify the displayed bundle ID, team, device fingerprint and profile date identify your intended Trio installation. Enter the exact existing Trio shared secret. Copy the maximum bolus and increment from your current Trio pump settings; the app supplies no default dose or suggested maximum. Inputs use decimal points, reject grouping/exponent notation, and require an exact multiple of the increment. The parser's technical configuration ceiling is 100 U; it is not a recommended dose or pump limit. Trio's own safety validator still makes its independent checks.
3. Import an APNs P-256 `.p8` key authorised for Trio's app topic, environment and team, and enter its Key ID. A saved Mac key may be reused only if the teams match and the key also authorises the Trio topic. Separate phone and Mac signing keys/teams are supported.
4. The Mac must also be registered with APNs, with its own return key saved in Command lab. **Stock Trio requires the Mac return APNs private key in `return_notification`.** TrioPC places it only inside the shared-secret-encrypted command, then sends that ciphertext through Apple to your phone. This key delegation is disclosed in the review sheet. A return-topic-scoped key can limit its authority where supported; never publish keys or tokens.
5. Save control settings in Keychain, verify the target/limits checkbox, and enable stock-Trio control for this session. A changed device token/target requires another explicit verification and save. Enabling is not retained across app launches.

## Manual send and outcome handling

### If Apple rejects the request

An HTTP 403 is an APNs authentication or permission rejection, not a Trio dose-validation response. Check the APNs key in Apple Developer before considering another request: its Key ID must match the imported `.p8` file and belong to the team shown for the phone. Its permitted apps and APNs environments must include the phone's Trio topic and environment. A key that works for the Mac may be restricted to the Mac app or development environment while the phone uses production. Do not change the discovered phone environment just to match a key, and do not send a bolus as a credentials test.

TrioPC retains only allowlisted Apple reason codes in the encrypted local attempt record and displays guidance alongside them. Unknown response content is not displayed or logged. Earlier versions discarded Apple's specific reason; those records remain readable but their missing reason cannot be reconstructed. The phone-review requirement and no-retry behavior apply to every committed attempt, including a rejection.

Apple's [APNs response reference](https://developer.apple.com/documentation/usernotifications/handling-notification-responses-from-apns) explains errors such as `InvalidProviderToken`, `ExpiredProviderToken`, `Forbidden` and `BadEnvironmentKeyIdInToken`.

Enter an amount yourself and choose Review bolus. Review does not send a command. The final button invokes macOS device-owner authentication (Touch ID or the Mac password). Unavailable/cancelled authentication blocks sending. The amount and target are frozen for that review, which expires after 60 seconds. TrioPC re-fetches the target and rechecks its local data freshness before sending. This prototype requires a Nightscout glucose reading no older than ten minutes and no more than one minute in the future; this check does not validate a dose.

Before any POST, an encrypted local attempt record is written atomically and synchronised to disk. Its key is a separate, device-only Keychain item, created without replacing an existing key. A file lock prevents cooperating TrioPC instances from opening the same bolus journal concurrently. An unresolved prior attempt, corrupt record, missing key or storage failure blocks sending.

The request is made once by application code, with `apns-expiration: 0`; no retry, scheduling or resend workflow exists. The APNs ID and journal UUID are local diagnostic identities, **not stock-Trio deduplication keys**. Stock Trio does not recognise a command UUID in this protocol. These local protections cannot guarantee exactly-once delivery across Apple, the operating system, another controller or a second Mac.

HTTP 200 means Apple accepted the request. A timeout does not establish rejection, and an Apple response does not establish insulin delivery. Every committed attempt requires an explicit phone review before a separate new request can be prepared. Record phone review only after checking Trio on the phone; this acknowledgement never records completed delivery or zero delivery and cannot resend the old attempt. The amount field is cleared after a committed attempt. Stock Trio's uncorrelated replies are displayed separately and never unlock the journal or advance it to a pump-completion state. A process restart leaves an interrupted attempt unresolved and performs no send.

The journal retains up to 1,000 local attempts, encrypted with AES-GCM. It includes requested units, time, app identity/fingerprint, submission evidence and the user's phone-review acknowledgement. It contains no shared secret, APNs private key or device token. Do not delete or reset the journal to work around an unknown outcome. Missing/corrupt storage needs deliberate recovery rather than automatic reset.

## Protocol and validation

The payload is `user: TrioPC`, `command_type: bolus`, a numeric `bolus_amount`, Unix `timestamp`, and the standard `return_notification` fields. Encryption is AES-256-GCM with SHA-256 of the exact shared-secret UTF-8 bytes, no associated data, and base64 of `nonce || ciphertext || tag`. This intentionally matches stock Trio and is separate from the optional history codec. The APNs wrapper contains `encrypted_data` and an alert APS dictionary with `content-available: 1`, matching the established LoopFollow path. Secrets and amounts do not appear in the outer plaintext wrapper.

Tests cover numeric validation, encryption/wire fields, write-before-network ordering, one-call transport behavior, duplicate/unresolved blocking, stale reviews, target mismatch, encrypted record recovery, wrong keys, corruption and locks. An isolated interoperability test also used **unmodified** Trio `SecureMessenger.swift` and `CommandPayload.swift` with its CryptoSwift dependency to decrypt a generated synthetic Mac payload successfully. No real phone command was used for verification.
